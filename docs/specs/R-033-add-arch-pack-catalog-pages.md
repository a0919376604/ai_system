## For future Claude
> R-033: spec for three new architecture-pack page types in `/draw-arch`: **modules**
> (an import-coupling matrix computed by a script), **jobs** (a background-program table
> checked against the code's registry) and **features** (one card per feature on a
> single page). The contract that the plan + build implement.

## Decisions

- Door: two-way — the change only adds optional spec fields, one stdlib script and page
  CSS inside `claude-skills/draw-arch/`. Existing diagram specs render byte-identically,
  and a revert removes it all. (my call)
- Ship all three in one row — operator: 「三點一起開成一列吧」.
- Trigger: the line-oa pack answered none of these: how many modules there are and how
  coupled they are; which background programs run (the overview shows two boxes, but
  `sweeper_specs.py` registers about 30); and how many features exist. (operator)
- One features page with a card per feature, not one page per feature. The operator
  offered either; at 30+ features, separate pages are hard to keep current. (my call,
  grilling Q1)
- Module numbers come from a script, never from Claude's reading. `modules.py` parses
  imports through `ast`, never importing or running the code, the same as the LangGraph
  check. (my call, Q2)
- A module is an immediate child (package directory or `.py` file) of a root the caller
  names. Granularity is chosen by the roots: `backend/app` gives api/core/domain/…;
  `backend/app/core` gives its files. No `--depth` flag. (my call, Q3)
- Coupling is shown as an import-count matrix plus fan-in, fan-out and the module-level
  cycles. No instability index or other derived scores. (my call, Q4)
- Jobs completeness is checked against code: a spec may name a registry (a file plus a
  call name such as `SweeperSpecMeta`). `check.py` reads each call's literal `name=` through
  `ast` and reports every registered name without a row. Rows outside the registry (for
  example a module's own worker) are allowed. (my call, Q5)
- The page type is a new top-level `page` field: `diagram` (default, today's behaviour),
  `table`, `cards` or `matrix`. Non-diagram pages need no `canvas`, `nodes` or `edges`.
  (my call, Q6)
- `table` is generic (columns named by the spec) rather than jobs-only, so the same
  renderer also serves later lists, such as API routes. (my call, Q7)
- The index orders overview, features, modules and jobs first, then the rest by topic.
  (my call, Q8)
- On a re-run, `modules.py` keeps the `does` text and title/subtitle Claude wrote into
  the existing output; only the numbers are recomputed. (my call, Q9)
- The real line-oa pack is regenerated by Claude after the build, with the screenshot
  read, as in R-029: a visual deliverable is not done until it is seen. (my call, Q10)

## Seams

| Seam | Interface | Guaranteed behavior |
|------|-----------|---------------------|
| page type | spec `page`: `diagram` \| `table` \| `cards` \| `matrix`; absent = `diagram` | `check.py` validates and `render.py page` renders each type. An absent `page` gives output byte-identical to before R-033. Only `diagram` requires `canvas`, `nodes` and `edges`. An unknown `page` is a `check: schema` finding and a render exit 2 with no output. |
| table page | `columns: [{key, label}]`, `rows: [{id, cells: {key: text}, src, warn?, group?}]`, optional `registry: {file, call, key?}` | Rendered as a `<table class="cat">` with the column labels as headers, rows in spec order, each `<tr id="row-<id>">` plus a 程式碼 column from `src`; `warn` gives the rose ⚠ row; rows sharing a `group` render under an `<h2>` of that group in first-seen order. Below 700 px, rows become cards. |
| registry check | `check.py <spec> --repo <repo>` with `registry` set | Parses `registry.file` through `ast` only; for each call whose callee name (`Name` or `Attribute.attr`) equals `registry.call`, takes keyword `registry.key` (default `name`) when it is a string literal. Reports `check: registry: missing row <name>` for each such name with no row `id`,
`check: registry: unresolved name at line <n>` for a matching call whose key is absent or not a string literal, and `check: registry: file not found` / `cannot parse`. Never imports or runs the file. |
| cards page | `cards: [{id, title, does, entry?, data?, topics?: [slug], jobs?: [id], src: [path:range]}]` | One `<article class="card" id="card-<id>">` per card in spec order. `topics` become links to `<slug>.html`, `jobs` become links to `jobs.html#row-<id>`. `check.py` reports `check: link: missing topic <slug>` when `<slug>.json` is absent beside the spec, and `check: link: missing job <id>` when `jobs.json` beside the spec has no such row. |
| modules script | `python3 lib/modules.py <repo> <out.json> --root <dir> [--root <dir> …] [--name <repo name>]` | Writes a `matrix` spec: `modules: [{id, root, files, lines, does?}]`, sorted by id, and `matrix[i][j]` = the number of import statements in module i that resolve to module j (i ≠ j; the diagonal is 0). A root also acts as a `sys.path` entry, so `--root src` resolves `import foo` to `src/foo`. When a stem appears under 2+ roots, its id is `<root path>/<stem>`; a `.py` file beside a same-named package is skipped (Python imports the package). Duplicate module ids are a `check: id: duplicate module <id>` finding. Imports are resolved for absolute imports and for relative imports that stay inside the repo; third-party and stdlib imports are ignored. `cycles` lists every strongly connected set of 2+ modules, each sorted, the list sorted. Test directories (`tests`, `test`, `*_test.py`, `test_*.py`) are skipped. `repo.commit` is HEAD of `<repo>`. Existing `does`, `title` and `subtitle` in `<out.json>` are preserved. Exit 2 with no output on a missing root. Deterministic. |
| matrix page | spec with `page: matrix`, `modules`, `matrix`, `cycles`, `roots` | Renders a heat table (cell shade by count, empty for 0), a per-module row of files / lines / fan-in / fan-out (fan-in = number of other modules importing it, fan-out = number of modules it imports), and the cycle list (or 「沒有循環依賴」). A caption above the heat table says it reads 列 → 欄. A two-module cycle reads `a ⇄ b`; a larger one reads `N 個模組互相循環：a、b、c`. `check.py --repo` recomputes the matrix from `roots` and reports `check: matrix: stale` when it differs. |
| index order | `render.py index <dir> <out>` | Lists `overview`, `features`, `modules`, `jobs` first (those present), then every other topic alphabetically. |
| skill workflow | `SKILL.md` step 2 | The default topic set adds `features`, `modules` and `jobs`; the steps say how each is produced (script, registry, cards). |

## Acceptance

- **AC-1** Given every existing fixture (`clean.json`, `minimal.json`, `lg.json`), when
  rendered, then the HTML is byte-identical to the pre-R-033 renderer.
- **AC-2** Given a `table` spec with two groups and one `warn` row, when rendered, then the
  page has one `<h2>` per group in first-seen order, `id="row-<id>"` on each row, one ⚠ row,
  and no `<svg`.
- **AC-3** Given a registry fixture file with three `Meta(name="…")` calls and a table spec
  listing two of them, when `check.py --repo` runs, then it exits 1 and prints exactly
  `check: registry: missing row <third>`; with all three rows it exits 0. The fixture's
  first line is `raise SystemExit(9)` and the exit status is never 9.
- **AC-4** Given a `cards` spec whose card links topic `nope` and job `ghost`, with a
  `jobs.json` beside it lacking `ghost`, when checked, then both `check: link:` findings
  print; when the links exist, it exits 0 and the page has `href="csat.html"` and
  `href="jobs.html#row-csat_worker"`.
- **AC-5** Given a fixture repo with packages `a`, `b`, `c` where a→b, b→a (relative import)
  and c→b twice, plus a `tests/` importing c and an `import os`, when `modules.py` runs with
  `--root` on that dir, then `matrix` counts a→b 1, b→a 1, c→b 2, all else 0; `cycles` is
  `[["a","b"]]`; tests are absent; a second run is byte-identical; a `does` edited into the
  output survives a re-run.
- **AC-6** Given that `modules.py` output, when rendered, then the page shows per-module
  fan-in/fan-out (b: fan-in 2, fan-out 1) and the cycle `a ⇄ b`; and after a source import
  is added, `check.py --repo` reports `check: matrix: stale`.
- **AC-7** Given a pack dir with `jobs`, `overview`, `csat`, `features`, `modules`, when
  indexed, then links appear in the order overview, features, modules, jobs, csat.
- **AC-8** Given `page: "bogus"`, then `check.py` reports a schema finding and
  `render.py page` exits 2 without writing the output.
- **AC-9** Given the new pages, then they keep the offline rules: no `<script`, no event
  handler attributes, no literal `http://` / `https://` URL, all spec text escaped.
- **AC-10** (done when) Given langlive-line-oa re-run with `/draw-arch`, then the vault pack's
  index links modules, jobs and features; jobs lists every name in
  `backend/app/core/sweeper_specs.py` (registry check clean) with type, schedule and code
  location; modules comes from `modules.py`; features has one card per feature; every page
  passes `check.py`, and a screenshot of each was read.
