# Brand direction procedure

Run after project resolution and before the inventory. The pick is the proposed authority for the scan; approved brand rules remain approved and conflicts must be listed.

`<evidence>` below is `Reports/<stem>.evidence` in the vault project, or the same path under the temporary report directory without a vault binding.

1. **Reuse check per surface.** Read the surface's section in `Reports/refactor-brand-direction.md`: `## app` for screens people work in, `## page` for public pages. If it exists and the operator did not say 「重選」 or "re-pick", load it, state 「沿用 <date> 選的方案 X」, and go to the inventory. Either phrase forces a new deal. A scope on another surface deals its own three. With no vault binding, deal and pick in the temporary report directory, persist nothing, and say the pick will be asked again next time.

2. **Resolve taste v2.** Use the first of these installs that holds `scripts/draw.mjs`, in this order: `~/.claude/skills/design-taste-frontend`, `~/.agents/skills/design-taste-frontend`, `~/.codex/skills/design-taste-frontend`. Also require `node --version` ≥ 22 and a Chrome. If any prerequisite is missing, skip this step and audit against existing brand sources. The human report's first screen says 「mockup 未驗證：沒有安裝 taste v2」 with the install command `npx skills add https://github.com/Leonxlnx/taste-skill --skill design-taste-frontend -g`; candidates' after-slots say 「未驗證」. Nothing is hand-drawn in their place.

3. **Capture one main screen.** Choose the highest-traffic screen in scope: the shared shell plus one key route, for example a chat inbox. Capture it at 1440 and 390 as 「現況」. Use one screen only.

4. **Deal three distinct directions.** Run from a scratch directory. Prefix every taste command in steps 4 and 5 (`draw.mjs`, `inspect.mjs`, `lint.mjs`) with `TASTE_SKILL_HISTORY="<evidence>/taste-history.json"` so the operator's global taste history is untouched; a shell variable does not survive between tool calls, so write the prefix on each command. For an app, use `draw.mjs --app --kind <kind> --screens <screen> --options 3`; for a page, use `draw.mjs --sector <sector> --sections <roles> --options 3`. If there are fewer than three distinct style/direction ids, top up with the other `--theme`, then the closest neighbouring kind/sector, until there are three distinct ids. If top-ups still give fewer than three, say how many and why before showing them; never present two silently. Use `--keep palette,type` only for values the approved brand source marks as fixed; the logo is always kept as an asset.

5. **Build each direction.** Deal each option in full first: the step-4 command without `--options`, plus `--style <id>` (app) or `--direction <id>` (page), prefixed with `TASTE_SKILL_HISTORY="<evidence>/taste-history.json"` and given `--out <evidence>/directions/<x>/.taste-skill` so the sheets do not overwrite each other. This full deal is the one that writes history. Then follow taste's own run: app `references/app-screens.md` §2.3–2.7, or the page run's steps. Use real labels and realistic repo data. Save live builds to `<evidence>/directions/<a|b|c>/index.html`; a mix (step 7) uses `<evidence>/directions/d/`. Run `inspect.mjs [--app]` on each, fix FAILs, and do at most three look-and-fix rounds as taste prescribes. Capture each build at 1440 and 390.

6. **Write and inspect the comparison mockup.** Read and follow the vault's Project Mockup Convention. Write `Proposals/mockups/refactor-brand-<stamp>-directions-mockup.html`: h1 + 「三個方案 · 待選」, `.sub`, `.banner`, `.panel.facts`, `.panel.now` with the current screenshots, and `.panel.optA`, `.panel.optB`, `.panel.optC`. Each option heading must start with `方案 A ·`, `方案 B ·`, or `方案 C ·` followed by a one-line idea, for Roadmap 檢視 matching (R-024). Include style id + seed, type, palette swatches, JPEG/PNG data-URI screenshots at 1440 and 390, `.notes` with 「好處」/「弱點」, and a relative link to its live build. Mark the recommendation with `.tag.rec`. Add `table.t` 「方案並排」 and 「需要你拍板」. Keep the file self-contained with no external URLs; use screenshots instead of live markup because Roadmap 檢視 strips scripts and taste's charts need JS. Without a vault binding, write the mockup beside the reports in the temporary report directory and link it by basename. Render with headless Chrome and look at the result before showing it.

7. **Stop for the pick and record it.** Ask 「選 A、B、C，或混搭（例如 A 的配色＋B 的字）」 and wait. For a mix, build it, add `.panel.optD` headed 「方案 D · …」 with its screenshots and live-build link, show it, and get confirmation before continuing. Silence or a general 「好」 is not a pick. Under the surface's `## app` or `## page` section of `Reports/refactor-brand-direction.md`, write: date, report stem, picked option, taste style/direction id + seed, kind/sector + theme, palette and type tokens, kept brand assets, comparison mockup path, and the operator's words. With no vault binding, retain the pick only for the current scan in the temporary report directory; persist nothing for future scans.
